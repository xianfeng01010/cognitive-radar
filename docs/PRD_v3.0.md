# 认知雷达（Cognitive Radar）产品需求文档 v3.0

**文档状态**：待评审  
**版本**：v3.0（整合完整版）  
**日期**：2026-07-14  
**核心原则**：真实 > 正确性 > 覆盖率 > 及时性

---

## 一、背景与问题

### 1.1 现状痛点

用户当前的信息获取来源存在五个根本缺陷：

| 渠道 | 缺陷 | 后果 |
|---|---|---|
| 朋友圈 | 被动接收，视野由人际关系决定 | 与自身无关的内容大量占据注意力 |
| 公众号 | 编辑替用户筛选，用户不知编辑偏好 | 认知被第三方编辑悄然塑造 |
| 抖音 | 短视频算法驱动，注意力碎片化 | 15秒内决定是否推送，同质内容无限循环 |
| 小红书 | 种草式内容主导，信息即广告 | "博主推荐"≠"真实体验"，软文混杂 |
| 算法推荐 | 封闭反馈回路，只喂已证明喜欢的内容 | 信息茧房越来越厚，信息差越来越大 |

**核心问题**：用户以为自己「在看世界」，实际上只是在「看自己的回音」。

#### 抖音的特殊问题

```
算法逻辑：完播率 + 互动率 + 关注转化

→ 内容必须在 3 秒内抓住注意力
→ 深度分析、复杂逻辑几乎没有生存空间
→ 同类话题无限循环（你看过1个AI工具视频 → 系统给你推100个）
→ 真正有价值的独立开发故事，被淹没在娱乐化内容中

结果：
  你知道的 ← 你刷到的 ← 算法认为你会看完的
                  ↑
            这三者高度重合
            但都与「你领域真正发生的事」有差距
```

#### 小红书的特殊问题

```
内容生态：种草即内容，内容即广告

→ 「真实分享」和「软文」的边界几乎不存在
→ 博主有变现动机（接单/带货），中立性存疑
→ 同一产品可能出现大量内容质量差异极大的帖子
→ 搜索结果严重受「博主粉丝量」影响

更隐蔽的问题：
→ 你以为你在「搜索真实经验」
→ 实际上你在看「被精心设计的种草内容」
→ 爆款 ≠ 客观真实

结果：
→ 信息来源表面上是「真实用户」
→ 本质上是「有商业动机的内容生产者」
→ 真实性和参考价值被系统性高估
```

#### 平台接入说明

抖音、小红书作为信息获取渠道具有重要价值，但其内容生态的特殊性（算法驱动/种草经济）决定了来自这两个平台的内容在进入「认知雷达」时必须经过更严格的可信度评估——具体规则见来源层和群众信号采集规范。

### 1.2 核心问题定义

```
你的认知 = f(朋友圈交集 + 订阅号编辑偏好 + 抖音算法 + 小红书种草 + 推荐算法强化)
vs
真实世界 = 你领域里实际在发生的事

→ 中间的差值，就是「认知雷达」要消除的信息差
→ 这个差值，随着你在抖音/小红书上刷得越多、算法喂得越精准，反而越大
```

### 1.3 平台定位

认知雷达（Cognitive Radar）

**不是**：
- ❌ RSS 阅读器
- ❌ 智能推荐
- ❌ 信息聚合工具

**而是**：
- ✅ 持续扫描用户关注领域的新变化
- ✅ 发现订阅覆盖不到的信息盲区
- ✅ 主动告诉你「你不知道但你需要知道的事」
- ✅ **反幻觉 · 自我校准 · 透明可审计** 的个人资讯智能代理

**一句话定义**：

> **认知雷达 = 搜索驱动的自生长信息网络。你搜索 → 系统从订阅中找答案 → 不够就拓展 → 发现新源建议订阅 → 订阅增长 → 低质源自动清理 → 信噪比持续优化。**

### 1.4 设计红线（铁律）

**任何情况下，以下红线不可突破：**

| 编号 | 红线内容 |
|---|---|
| R-01 | 推送的内容必须能枚举来源，否则不推送 |
| R-02 | 无印证的结论不得声称「这是真的」 |
| R-03 | 「找不到证伪证据」≠「这是真的」——最常见幻觉来源 |
| R-04 | 置信度 < 40 的内容，不得主动推送给用户 |
| R-05 | 系统犯错必须主动告知用户，不得掩盖 |
| R-06 | 出处树不可删除或修改，历史不可篡改 |
| R-07 | 用户反馈数据不得用于推送优化以外的用途 |
| R-08 | 系统不得因为「用户想知道答案」而降低推送门槛 |

**透明性要求**：
1. 每条推送必须附带「真实度报告」
2. 每个来源的信任分必须对用户可见、可查、可审计
3. 系统每周必须报告自身健康状态
4. 系统规则的任何变更必须通知用户并可回滚
5. 无印证状态必须明确表达，不可沉默或模糊

| 阶段 | 时间 | 目标 | 核心交付 |

## 三、产品形态

### 3.1 主交互：Telegram Bot

**理由**：
- 目标用户（开发者/技术人员）使用率高
- Bot推送天然就是"校准"形态：有事找你，没事不打扰
- 回复即可反馈（👍/🤔/👎）
- 开发维护成本低

**核心命令**：
```
/scan [关键词]       → 搜索并生成全景报告
/sources            → 查看订阅源信任分
/health             → 查看系统健康报告
/web                → 打开Web看板链接
/restore            → 恢复已清理的订阅源
/history            → 查看最近10条流量历史
/history search     → 仅搜索历史
/history view       → 仅浏览历史
/history search [关键词] → 搜索历史中的关键词
/delete history [id] → 删除单条历史
/delete history all  → 删除全部历史（需二次确认）
/delete history search → 删除所有搜索历史
/delete history view   → 删除所有浏览历史
```

### 3.2 辅助界面：轻量Web看板

**只做四个页面**：
- **最近推送**：按时间排列的推送历史，可展开看出处树
- **来源管理**：订阅源列表 + 信任分 + 状态（L1/L2）
- **系统健康**：每周报告 + 茧房检测 + 消息栈
- **流量历史**：搜索历史 + 浏览历史，支持删除/复制

**不做**：
- ❌ 瀑布流/信息流
- ❌ 话题分类浏览
- ❌ 收藏/稍后读
- ❌ 个性化推荐

### 3.3 设计原则：一屏一事

用户90%时间在推送卡片上，不需要"刷"，只需要"看"。

```
🚀 [已印证] Cursor 发布 Agent Mode 2.0

来源: Cursor官方博客 (信任分 85, L1)
印证: 3个独立来源 ✅
     ├─ TechCrunch 报道
     ├─ HN #38492 (127 upvotes)
     └─ GitHub Release

📊 真实度：高 | 话题：AI编程工具

[✅ 有价值] [🤔 存疑] [❌ 无价值]
```

## 四、核心交互模式

系统支持两种交互模式，用户可混合使用：

### 4.1 搜索模式（主动探索）

**触发方式**：用户输入 `/scan [关键词]`

**适用场景**：
- 用户有明确的信息需求
- 想了解某个领域的全貌
- 需要决策支持（选A还是B）

**输出形态**：
- 根据搜索词强弱，决定输出案例/信息列表
- 自动聚类生成维度（不预设）
- 发现新源时建议订阅

### 4.2 推送模式（被动接收）

**触发方式**：系统主动推送

**适用场景**：
- 用户不想主动搜索
- 重大事件发生时第一时间通知
- 定期健康报告

**输出形态**：
- 三档推送（已印证/待验证/观察中）
- 优先推送L1源内容
- 每天3-10条，有事找你，没事不打扰

## 五、来源层（Source Layer）

### 5.1 来源分类与初始信任分

| 类型 | 定义 | 示例 | 初始信任分 |
|---|---|---|---|
| A类 | 官方来源，一手持握 | 官方博客、GitHub Release、官方公告 | 85 |
| B类 | 权威媒体，有采编能力 | The Verge、TechCrunch、36kr | 75 |
| C类 | KOL/专家/社区领袖 | Twitter/X、Newsletter、B站up主、抖音/小红书认证博主 | 50 |
| D类 | 群众信号 | GitHub Issue、HN评论、论坛讨论、Product Hunt评论 | 40 |
| E类 | 社交平台公开内容（高噪音） | 抖音评论区、小红书笔记/评论、微博公开帖 | 25 |

### 5.2 初期信息来源优先级

| 阶段 | 信息来源 | 备注 |
|---|---|---|
| 第一阶段 | RSS（用户自选订阅源） | 验证核心逻辑 |
| 第二阶段 | GitHub Issues + HackerNews | 有官方/高质量API |
| 第三阶段 | Reddit / Product Hunt / V2EX / 小红书笔记（第三方） | 非核心，逐步接入 |
| 待定 | 抖音内容 | 无官方API，依赖用户手动提交或第三方数据服务 |

#### 平台接入风险说明

```
微信公众平台：无公开API，无法接入。任何声称能获取微信内容的服务均涉及平台规则风险。
抖音：无官方公开API，内容获取受严格限制。可通过第三方数据服务接入（需商业授权），或人工手动指定关键词订阅。
小红书：无官方公开API，笔记搜索可通过第三方服务实现（非官方途径，存在账号封禁风险）。
策略建议：抖音和小红书以「用户主动提交有价值内容」为主要采集方式。
```

### 5.3 来源输入规范

所有进入系统的内容，必须携带以下元数据：

```json
{
  "content": "原始内容全文",
  "url": "原始链接",
  "platform": "来源平台",
  "author": "发布者标识",
  "published_at": "发布时间（UTC）",
  "collected_at": "采集时间（UTC）",
  "content_type": "bug_report | experience | data_claim | prediction | news | social_media_post",
  "language": "zh | en",
  "platform_type": "A | B | C | D | E",
  "keywords": ["提取的关键词"]
}
```

## 六、两级缓存池机制

### 6.1 整体架构

```
┌─────────────────────────────────────────┐
│  L1 一级缓存池（核心订阅）              │
│  • 预设 / 经考察晋升的高质量源          │
│  • 搜索时优先检索                       │
│  • 推送时优先选用                       │
│  • 容量上限：50个                       │
└────────────────┬────────────────────────┘
                 │ 晋升（命中次数≥阈值 + 信任分≥65 + 质量通过率≥60%）
┌────────────────▼────────────────────────┐
│  L2 二级缓存池（候选订阅）              │
│  • 拓展搜索自动发现的新源               │
│  • 考察期：30天                         │
│  • 容量上限：200个                      │
│  • 超时未命中 → 自动移除                │
└────────────────┬────────────────────────┘
                 │ 淘汰
┌────────────────▼────────────────────────┐
│  回收站（30天内可恢复）                 │
└─────────────────────────────────────────┘
```


#### L1 特权

| 特权 | 说明 |
|---|---|
| 搜索优先 | 用户搜索时，先查L1源，L1不够才拓展 |
| 推送优先 | 同一事件多个源报道，优先选L1源的内容 |
| 展示权重 | 报告中L1源的内容排在前面 |
| 信任分保护 | L1源信任分下限不低于40（给纠错机会） |

#### L1 降级规则

```
L1源 → 信任分 < 30 持续14天 → 降级到L2
L1源 → 90天无更新 → 降级到L2 + 通知用户
L1源 → 推送通过率 < 10% 持续30天 → 降级到L2
```

### 6.3 L2 二级缓存池

#### 入池规则

```
拓展搜索发现新内容
    ↓
追溯来源（作者/平台/频道）
    ↓
该来源不在L1也不在L2？
    ├─ 是 → 自动加入L2
    │       记录：入池时间、来源、首次命中的搜索关键词
    └─ 否 → 更新命中计数
```

#### L2 数据结构

```json
{
  "source_id": "src_xxx",
  "url": "https://...",
  "name": "@policy_watcher",
  "platform": "hn",
  "added_at": "2026-07-01T10:00:00Z",
  "added_by_search": "自主创业",
  "level": "L2",
  "trust_score": 58,
  
  "hit_tracking": {
    "total_hits": 3,
    "hits": [
      {
        "search_keyword": "自主创业",
        "time": "2026-07-03T14:00:00Z",
        "hit_type": "direct"
      }
    ],
    "last_hit": "2026-07-12T16:00:00Z",
    "days_since_last_hit": 2
  },
  
  "quality_metrics": {
    "content_count": 5,
    "verified_count": 3,
    "verification_rate": 0.60,
    "avg_trust_of_content": 62
  },
  
  "promotion_eligible": false,
  "expiry_time": "2026-07-31T10:00:00Z"
}
```

### 6.4 "命中"的定义

| 命中类型 | 定义 | 权重 |
|---|---|---|
| 直接命中 | 用户搜索关键词A → 拓展搜索 → 该源的内容被检索到 | ×1.0 |
| 间接命中 | 用户搜索关键词B → 检索到内容X → 内容X引用了该源 | ×0.5 |
| 推送命中 | 该源的内容被推送 → 用户点击查看详情 | ×1.5 |
| 印证命中 | 该源的内容印证了其他源的信息 | ×1.2 |

**加权命中分** = Σ(每次命中 × 对应权重)

### 6.5 晋升规则（L2 → L1）

```
晋升条件（全部满足）：
① 入池 ≥ 14天（最低考察期）
② 累计加权命中分 ≥ 4.0
③ 信任分 ≥ 65
④ 内容质量通过率 ≥ 60%（被印证的内容占比）
⑤ L1当前数量 < 50（容量上限）
```

晋升通知：
```

考察期表现：
• 入池 18天，命中 7次
• 信任分：58 → 72
• 内容印证率：71%
• 覆盖话题：科技政策、合规、AI监管

已自动加入一级缓存池
[📊 查看详情] [⬇️ 降回候选]
```

### 6.6 淘汰规则（L2 → 回收站）

```
淘汰条件（满足任一）：
① 入池30天，命中 = 0次 → 直接移除
② 入池14天，命中 < 2次 → 移除
③ 最后一次命中距今 > 60天（2个月） → 移除
④ 信任分 < 25 → 移除
```

淘汰通知（批量，不逐条打扰）：
```
🧹 本周自动清理：3个候选源已移除

• @ai_tools_daily — 20天0命中
• @crypto_signal — 信任分降至18
• r/oldforum — 60天无命中

如需恢复：/restore
```

### 6.7 关键参数汇总

| 参数 | 值 | 说明 |
|---|---|---|
| L1容量上限 | 50 | 防止核心源过多导致信噪比下降 |
| L2容量上限 | 200 | 给足考察空间 |
| L2最低考察期 | 14天 | 防止冲动晋升 |
| L2晋升命中阈值 | 加权命中分 ≥ 4.0 | 直接×1.0, 间接×0.5, 推送×1.5, 印证×1.2 |
| L2晋升信任分 | ≥ 65 | 确保质量 |
| L2晋升质量通过率 | ≥ 60% | 内容要被印证 |
| L2淘汰：30天0命中 | 移除 | 完全无用 |
| L2淘汰：14天<2命中 | 移除 | 价值太低 |
| L2淘汰：60天无命中 | 移除 | 已失去相关性 |
| 回收站保留期 | 30天 | 可恢复 |

## 七、缓冲池（Buffer Pool）

### 7.1 入池规则

**✅ 进入缓冲池**：
```
单个独立来源首次报道 → 自动入池
3+ 独立来源印证 → 跳过缓冲池，直接推送
```

**❌ 不进入缓冲池**：
```
来源可信度 < 20 → 直接归档，不推送
内容重复（5个以上来源已报道同一事件）→ 合并处理
```

**🔄 入池后状态流转**：
```
pending → verifying → confirmed / debunked / expired
```

```json
    "trust_score": 72,
    "author_handle": "@username",
    "person_id": "hash_of_handle",
    "cache_level": "L1 | L2"
  },
  "verification": {
    "status": "pending | verifying | confirmed | debunked | expired",
    "search_count": 3,
    "search_results": [],

  }

```

### 7.3 验证优先级计算

```
验证紧迫度 = 信任分 × 信息价值权重 × 时间衰减因子
```

### 7.4 信息类型权重表

| 信息类型 | 权重 | 说明 |
|---|---|---|
| 重大事件（融资/收购/重磅发布） | ×3.0 | 最高优先级 |
| 行业动态（工具更新/功能变化） | ×2.0 | |
| 用户体验（Bugs/使用问题/评测） | ×1.5 | |
| 数字/数据类声明 | ×2.5 | ⚠️ 数字易夸大，自动标注 |
| 趋势预测 | ×1.0 | 天然不确定，降低预期 |
| 个人经历/故事 | ×0.8 | 主观参考价值有限 |

### 7.5 时间衰减因子表

| 时间窗口 | 衰减因子 | 说明 |
|---|---|---|
| 0-24小时 | ×1.0 | |
| 1-3天 | ×0.8 | |
| 3-7天 | ×0.5 | |
| 7天以上 | ×0.2 | 推送归档通知后降入观察池 |

### 7.6 硬性上限规则

```
⚠️ 任何缓冲池内容不得仅凭「紧急度高」而升级为主动推送。
必须同时满足：已有 ≥ 1 个独立印证来源。
```

## 八、信任分体系（Trust Score System）

### 8.1 三层分层架构

```
┌────────────────────────────────────────────┐
│     综合信任分（展示用，仅供参考）           │
│     用途：列表排序、初始筛选权重             │
│     警告：综合分可能掩盖话题差异性           │
└──────────────────────┬─────────────────────┘
                       │ 加权平均
┌──────────────────────▼─────────────────────┐
│         话题分（核心判断依据）                │
│  「此人在 AI 编程工具 话题上的可信度」        │
│  → 不同话题独立计算，互不影响                │
│  → 数据稀疏时（<5次发言）显示「数据不足」    │
└────────────────────────────────────────────┘
                       │
┌──────────────────────▼─────────────────────┐
│          类型分（精细校准）                   │
│  「此人在 AI 编程 话题的 Bug报告类发言可信度」 │
│  → 细分内容类型，精准校准                    │
│  → 数字类声明系统自动降权                    │
└────────────────────────────────────────────┘
```

**分期说明**：
- 第一阶段：仅实现综合信任分（单层）
- 第二阶段：实现话题分
- 第三阶段：实现类型分

### 8.2 话题维度（第二阶段）

预设话题（用户可自定义增删）：
```
AI编程工具      —— Cursor/Copilot/Claude Code等
独立开发者      —— 独立开发者的产品、收入、故事
市场分析        —— 行业趋势、市场数据、竞争格局
融资动态        —— 公司融资、收购、上市
技术原理        —— 技术实现、架构讨论、学术论文
开发者体验      —— 使用体验、效率对比、团队实践
```

### 8.3 类型维度（第三阶段）

| 类型 | 描述 | 初始权重上限 | 说明 |
|---|---|---|---|
| Bug报告 | 具体问题描述，可复现 | 95 | 描述型，最可信 |
| 实测数据 | 有具体数字的测试结果 | 90 | 有据可查 |
| 体验分享 | 主观使用感受 | 75 | 参考价值中等 |
| 价格/数据 | 涉及金钱/数量声明 | 60 | ⚠️ 数字易夸大，需标注 |
| 趋势预测 | 对未来的判断 | 50 | 天然不确定 |
| 争议/批评 | 对某事物的批评意见 | 68 | 通常比宣传保守 |

### 8.4 动态调整规则

**正向调整（印证）**：
```
上升幅度 = 5 / 总发言数
说明：发声越多，需要越多印证才能维持高分
例：100次发言中印证了60次 → 每次印证仅 +0.08分
例：10次发言中印证了8次 → 每次印证约 +0.5分
```

**负向调整（证伪）**：
```
被第三方证伪（非官方）：-15分（无门槛）
被官方辟谣：-20分
被用户标记「不准确」（累计3次）：-3分
```

**时间衰减**：
```
30天无活跃：-2分/天
```

### 8.5 置信区间规则

```
样本数 < 5：显示「数据不足，参考性有限」
样本数 5-20：显示分数范围（如 65-78）
样本数 > 50：精确到整数
```

### 8.6 下限规则

```
< 20分 → 进入「黑名单观察」，不自动推送
< 10分 → 暂停推送，需用户手动确认恢复
任何分数均可通过新的印证被提升，无永久封禁
```

### 8.7 信任分展示规范（用户界面）

```
┌──────────────────────────────────────────┐
│ 📊 @username 综合信任分：72/100           │
│    （基于 47 次发言，34 次印证）            │
│                                          │
│ 按话题：                                  │
│   AI编程工具     ████████████░░  82 ⭐   │
│   独立开发者     ███████████░░░░  71      │
│   市场分析       █████████░░░░░░  55      │
│   融资动态       ████░░░░░░░░░░░  38 ⚠️   │
│                                          │
│ 按发言类型（在「AI编程工具」话题下）：       │
│   Bug报告        ████████████████  95 ⭐ │
│   数字/数据      █████████░░░░░░  58 ⚠️  │
│   趋势预测       ██████░░░░░░░░  45      │
│                                          │
│ ⚠️ 融资动态数据不足（仅3次发言）            │
│    当前分数参考性有限                       │
│                                          │
│ 📈 趋势：近3个月 +8（活跃且准确）          │
│ 🕐 最近发言：3天前                         │
│ 📍 缓存池层级：L1 / L2                    │
└──────────────────────────────────────────┘
```

### 8.8 信任分双向阻力

**防止通胀（上升有阻力）**：
```
每次印证上升幅度 = 5 / 总发言数
```

**防止僵化（下降有速度）**：
```
被证伪：-15分（无门槛）
被官方辟谣：-20分
30天无活跃：-2分/天
```

### 8.9 季度校准（防止漂移）（第三阶段）

```
每季度随机抽取10%来源，用用户反馈数据验证信任分是否匹配实际
如系统性偏高/偏低 > 10% → 执行全局校准，推送通知用户
```

```
意图拆解：
├─ 核心意图：找副业/side project

├─ 中文词：["海外副业", "出海", "跨境独立开发"]
```

### 10.2 搜索词强弱判断

**判断标准**：
- 包含"如何/怎么/方法/经验"等词
- 涉及决策过程（选择A还是B）
- 有明确的行动目标
- 可以从他人经验中学习

**示例**："我想拓展海外副业"、"如何降低获客成本"

**输出要求**：≥3个真实案例 + 规律提炼

**报告结构**：
```
① 维度名称 — 真实案例
   ┌─ 案例1 ─────────────────────────────┐
   │ 🧑 谁 · 背景                        │
   │ 产品/项目：xxx                      │
   │ 结果：$0 → $3,000/月（6个月）       │
   │                                     │
   │ 时间线：                            │
   │ 3月 开始做...                       │
   │ 5月 转向...                         │
   │ 7月 达到...                         │
   │                                     │
   │ 关键决策：                          │
   │ ✅ 决策A（原因）                    │
   │ ❌ 决策B（踩坑）                    │
   │                                     │
   │ 📊 可信度：高 ✅                    │

   └─────────────────────────────────────┘

   📊 从案例中提炼的规律：
   • 共性：...
   • 差异：...

   💡 建议：...
```

#### 中等搜索词（有案例则输出，无则不强制）

**判断标准**：
- 询问"什么/哪些/现状"
- 关注事实和数据
- 案例是加分项，不是必须

**示例**："AI编程工具最新动态"、"独立开发者收入情况"

**输出要求**：有案例就展示，无案例则提供数据/信息列表

**报告结构**：
```
① 维度名称
   结论：一句话总结

   具体数据：
   • 数据点1
   • 数据点2

   📊 可信度：高 ✅ (N个独立来源印证)
   ├─ [L1] 来源1 (信任分XX)
   ├─ [L1] 来源2 (信任分XX)
   └─ [L2] 来源3 (信任分XX)

   💡 建议：...
```

#### 弱搜索词（不输出案例，只提供信息）

**判断标准**：
- 主观评价类（好不好玩/好不好吃）
- 纯时效信息（本周末活动/最新价格）
- 无法从他人经验中学习（每个人的偏好不同）
- 系统覆盖不足（订阅网络不相关）

**示例**："周末去哪里玩"、"今天天气怎么样"

**输出要求**：信息列表 + 可信度标注，不强行提炼案例

**报告结构**：
```
⚠️ 系统提示：
当前订阅网络（技术/创业类）不覆盖此类信息
本次结果完全来自拓展搜索，可信度参差不齐

① 官方信息（可信度高）
   🏛️ 信息1
   • 来源：官方渠道 (信任分95)
   • [查看官网]

② 用户评价（主观信息，需谨慎参考）
   📝 评价1
   • 来源：用户评价 (信任分58)
   • ⚠️ 单个用户评价，仅供参考

📊 本次扫描总结
   高可信信息：N条（官方信息）
   中可信信息：M条（用户评价）
   真实案例：0个（信息不足，无法提炼）

⚠️ 红线合规声明：
• 本报告中"好不好玩"属于主观评价，系统无法验证真实性
• 官方信息（时间/门票）可信度高，主观推荐仅供参考
```

### 10.3 三阶段检索

```
Phase 1：查 L1（一级缓存池）
├─ 扫描所有L1源，匹配关键词
├─ 结果：N条
└─ 评估：内容是否足够？缺失哪些维度？

Phase 2：查 L2（二级缓存池）
├─ 扫描所有L2源，匹配缺失维度
├─ 结果：M条
└─ 更新命中计数

Phase 3：拓展搜索（L1+L2都不够时）
├─ 搜索器：HN / GitHub / Reddit / Google News
├─ 结果：K条
├─ 新发现源 → 加入L2
└─ 已有源 → 命中+1
```

### 10.4 自动聚类

```
全部内容：L1(N) + L2(M) + 拓展(K) = Total条
    ↓
语义聚类（不预设维度）
    ↓
按信息密度排序：
├─ 维度1：信息数量最多 + 平均信任分最高 + 时效性最新
├─ 维度2：次之
└─ ...
    ↓
阈值过滤：维度内内容 < 2条 → 不单独成维度
```

### 10.5 案例提取规则

**案例识别规则（满足3条以上即提取为案例）**：
```
① 有具体的人/账号（不是泛泛的"有人说"）
② 有具体的时间线（"3个月后"、"2026年6月"）
③ 有具体的数字（收入、用户数、时间投入）
④ 有决策过程（"我选择了X因为Y"）
⑤ 有结果（成功/失败/踩坑）
⑥ 可溯源（有原始链接）
```

**案例可信度标注**：
```
高可信 ✅：来源信任分≥70 + ≥2个独立来源印证 + 有具体数字
中可信 ⚡：来源信任分50-69 + 1个印证来源
低可信 🔮：来源信任分<50 或 无印证
```

**推送内容（低打扰模式）**：

```
标题

⚠️ 来源可信度偏低
⚠️ 目前 0 个印证来源
⏱️ 已追踪：48小时

系统将持续追踪7天，有更新时通知

[保持关注 · 系统自动追踪]
[降低优先级 · 仅在搜索时出现]
[忽略 · 低于阈值后自动移除]
```

### 11.2 推送优先级

```
同一事件被多个源报道：

L1源报道（信任分85）  ← 优先推送，标注"已印证"
L2源报道（信任分68）  ← 作为印证来源，不单独推送
新源报道（信任分55）  ← 仅作为参考，不推送
```

### 11.3 推送禁止规则

| 规则编号 | 规则内容 |
|---|---|
| R-01 | 置信度 < 40 的内容，永远不得主动推送给用户 |
| R-02 | 「找不到证伪证据」不得被视为「内容为真」的依据 |
| R-03 | 「多个KOL相信」不得视为「多源印证」（KOL之间常互相引用） |
| R-04 | 系统不得因「用户想知道答案」而降低推送门槛 |
| R-05 | 推送必须附带完整来源列表，不可隐去任何来源 |
| R-06 | 「系统推断」类结论必须翻译为「可枚举的原始信号」 |

### 11.4 用户反馈机制

| 用户操作 | 系统影响 |
|---|---|
| [👍 值得关注] | 该内容验证权重 +20%；该来源信任分 +1 |
| [🤔 存疑] | 该内容留在观察池；该来源信任分不变 |
| [👎 无价值] | 该内容移出推送队列；该来源信任分 -2 |
| 主动点击「不准确」 | 该来源信任分 -3（累计3次触发正式警告） |

**⚠️ 重要约束**：
```
负反馈不应用于「强化推荐」——只能用于「校准信任分」。
不得将「用户点击了」等同于「用户认可了内容真实性」。
```

## 十二、验证层（Verification Layer）

### 12.1 主动追踪验证流程

#### Step 1：入池 → 生成验证任务

```
从原始内容提取关键词 + 同义词 + 扩展话题词
例：「Cursor 0.5」→ ["Cursor 0.5 release", "Cursor agent mode", "Cursor new version update"]
```

#### Step 2：多搜索器交叉验证

```
必须使用 ≥ 2 个不同搜索器同时搜索
允许的搜索器：Google News / HackerNews / 官方RSS / Semantic Scholar / Reddit
规则：≥ 2 个搜索器返回印证结果 → 判定为「有印证」
官方Blog/官方Twitter 印证 → 直接通过，无需交叉
```

#### Step 3：验证周期调度

| 时间窗口 | 搜索频率 | 说明 |
|---|---|---|
| 0-48小时 | 每2小时一次 | 最多24次 |
| 3-7天 | 每6小时一次 | 最多16次 |
| 7天以上 | 停止主动搜索 | 仅保留档案记录 |

#### Step 4：结果分级处理

```
印证成功（≥2源）→ 升级为「confirmed」，推送「验证更新」
被官方辟谣 → 标记为「debunked」，推送「撤回通知」
7天无印证 → 标记为「expired」，推送「归档通知」
```

### 12.2 印证溯源存档（Provenance Tree）

每当系统产生推送结论，必须同步生成并永久保存出处树：

**出处树规则**：
```
① 任何结论的来源必须可枚举、可点击回溯
② 出处树创建后不可删除或修改
③ 任一节点被证伪 → 整棵树标记「受影响」，生成新版本
```

### 12.3 「无印证」的诚实表达规范

当搜索印证返回0个结果时，系统必须立即诚实表达：

**错误做法（禁止）**：
```
默默继续等待 → 用户收不到任何反馈 → 以为「可能没问题」
推送时不提「无印证」→ 误导用户以为已验证
```

**正确做法（强制）**：
```
📌 [无印证] X 消息已追踪 48 小时

⏱️ 追踪时长：48小时
🔍 搜索范围：Google News / HN / 官方RSS / Semantic Scholar
📊 印证数：0 / 3 搜索器

⚠️ 系统结论：
   目前无足够证据判断真假
   「无印证」≠ 「消息为假」
   「无印证」≠ 「消息为真」

📌 你可以：
   A. 保持关注（系统持续追踪7天）
   B. 降低提醒（仅在有更新时通知）
   C. 忽略（低于阈值后自动清理）
```

### 12.4 验证搜索速率保护

| 场景 | 规则 |
|---|---|
| 单个缓冲池信息 | 48小时内：每2小时一次（最多24次）；3-7天：每6小时一次；超过7天：停止 |
| API返回速率限制 | 立即暂停该来源搜索，推送通知，不触发系统级告警 |
| 搜索超时（>30秒） | 标记为「搜索失败」，不计入印证/无印证；连续3次切换备用搜索器 |

## 十三、群众信号采集（第二阶段）

### 13.1 信号来源矩阵

| 类型 | 来源 | 采集难度 | 价值评级 |
|---|---|---|---|
| Issue类 | GitHub Issues/PR/Discussions | ⭐ 低（官方API） | ⭐⭐⭐⭐⭐ |

| 评测类 | App Store / Google Play | ⭐⭐（官方API有限） | ⭐⭐ |

### 13.2 价值初筛（Signal Scoring）

```
价值分 = 信息类型权重 × 来源可信度 × 具体程度因子
```

| 信息类型 | 权重 | 说明 |
|---|---|---|
| Bug报告 | ×2.0 | 高价值 |
| 实测数据 | ×2.5 | 极高价值，难造假 |
| 坑/警告 | ×1.8 | 用户急需 |
| 使用技巧 | ×1.2 | 有用但非关键 |
| 主观感受 | ×0.8 | 低权重 |

**决策阈值**：
```
≥ 3.5 → 直接进入验证层
2.0-3.5 → 进入待评估缓冲池
< 2.0 → 丢弃或存档
```

**去噪规则**：
```
纯表情包 / 「赞」「+1」→ 删除
明显广告/推销 → 删除
HN upvotes < 10 → 降权处理
```

### 13.3 GitHub Issues 采集规范

采集内容：
```
Issue 标题 + 正文（问题描述 = 第一手使用反馈）
Issue 评论（开发者之间的讨论）
PR 评论（代码审查中的技术讨论）
Discussions（社区问答，往往有深度内容）
```

| 状态 | 定义 | 行为 |
|---|---|---|

```

不自动删除（防止误伤新晋优质源），需用户确认
```

## 十五、反幻觉机制（Anti-Hallucination）

### 15.1 四层幻觉防御体系

| 层级 | 名称 | 机制 |
|---|---|---|
| 第一层 | 入口过滤 | 内容进入系统前，检查是否有可枚举的原始来源。无来源 → 不进入系统 |
| 第二层 | 验证过程约束 | 多搜索器交叉验证（≥2个不同搜索器）。印证结果必须有原始URL，不可仅凭「系统推断」 |
| 第三层 | 输出诚实性校验 | 推送结论必须附带完整出处树。无印证时必须诚实表达「无印证」。低置信度内容不得升级推送 |
| 第四层 | 事后回溯学习 | 每周负面学习回路，检视历史推送。发现幻觉立即回溯原因，更新规则 |

### 15.2 验证过程的自我校验

**问题**：验证搜索本身可能有偏见。

**例**：
```
系统想验证「X工具融资1亿美元」
→ 用关键词「X工具 融资」搜索
→ 返回的结果都是「X工具 融资1亿美元」
→ 系统以为找到了印证 → 实际只是原信息的复制
```

**对策**：
```
① 强制多搜索器交叉：同一关键词必须在 ≥2 个不同搜索器返回印证
② 搜索词扩展校验：主动构造「反驳搜索」（「X工具 辟谣 / 澄清」），有结果则重新评估
③ 利益相关方排除：印证来源与原来源有重叠作者/引用关系 → 不计入「独立来源印证」数量
```

### 15.3 负面学习回路（Critical Feedback Loop）（第三阶段）

**独立运行，每周日晚间执行**：
```
① 随机抽取最近推送的「高可信」内容（≥5条）
② 对每条内容验证：后来是否被官方更正/证伪/有新事实改变结论？
③ 如发现证伪/重大更正 → 触发证伪回溯
```

**回溯分析报告结构**：
```
🔴 证伪回溯报告

问题内容：「X工具月活超1000万」
推送时间：2026-07-08     推送置信度：85分

问题发现：2026-07-12 官方公告月活为 200万

回溯分析：
① 出处树中，哪一步出了问题？
   → 原始来源为「C类KOL」，引用「行业报告」
   → 行业报告实为付费软文，未披露利益关系

② 印证来源是否有问题？
   → 2个印证来源均为该KOL的二次引用
   → 不属于独立来源（违反了独立来源定义）

③ 信任分体系是否需要修正？
   → 建议增加：「利益相关方」排除规则
   → 建议增加：「付费内容」识别标记

系统修正：
→ 新增规则：印证来源必须与原来源非同源引用
→ 来源信任分：@xxx -10分（付费软文未披露）
```

## 十六、稳定运行机制（Stability）（第三阶段）

### 16.1 信任分双向阻力

**防止通胀（上升有阻力）**：
```
每次印证上升幅度 = 5 / 总发言数
例：100次发言中印证了60次 → 每次印证仅 +0.08分
例：10次发言中印证了8次 → 每次印证约 +0.5分
```

**防止僵化（下降有速度）**：
```
被证伪：-15分（无门槛）
被官方辟谣：-20分
30天无活跃：-2分/天
```

**季度校准（防止漂移）**：
```
每季度随机抽取10%来源，用用户反馈数据验证信任分是否匹配实际
如系统性偏高/偏低 > 10% → 执行全局校准，推送通知用户
```

### 16.2 断路器（Circuit Breaker）

**触发条件（任一满足，暂停推送）**：

| 条件 | 定义 |
|---|---|
| A. 推送可信度均值 < 60 | 连续3天所有主动推送平均分低于60 |
| B. 验证成功率 < 20% | 连续24小时，缓冲池内容无任何印证 |
| C. 用户负反馈率 > 15% | 最近100条推送，>15条被用户标记「不准确」 |
| D. 来源雪崩 | 单日 > 5个高信任来源（>75分）评分骤降 |

**断路器触发后行为**：
```
① 立即停止所有主动推送（保留后台验证）
② 生成告警报告，推送用户
③ 用户选择：「系统自检后恢复」/「人工介入排查」/「降低频率继续」
```

### 16.3 重大决策冷静期

| 决策类型 | 冷静期 | 用户确认 |
|---|---|---|
| 升级为「高可信」推送 | 6小时 | 不需要 |
| 高信任源（>75分）降分 | 24小时 | 需要 |
| 修改核心验证规则 | 72小时 | 需要 |
| 取消订阅源 | 即时执行 | 7天内可撤销 |

## 十七、自动清理机制（两层）

### 17.1 第一层：信任分降权（持续低分）

```
• 信任分 < 30 持续30天 → 自动降权（权重×0.3）
• 信任分 < 20 持续14天 → 自动归档 + 通知用户
• 任何时刻信任分回升 > 50 → 自动恢复
```

通知模板：
```
⚠️ @xxx 信任分持续偏低（当前28分）
已自动降权，不再参与推送
最近表现：10条内容中仅2条被印证
[🔄 恢复] [🗑️ 取消订阅] [📊 查看详情]
```

### 17.2 第二层：活跃度管理（长期无更新）

```
• 30天无更新 → 标记为休眠（权重×0.5）
• 90天无更新 → 自动归档 + 通知用户
• 归档后7天内用户可撤销
```

通知模板：
```
💤 @xxx 已90天无更新，自动归档
最后更新：2026-04-15
[🔄 恢复] [🗑️ 确认删除]
```

### 17.3 自动清理的执行原则

**做**：
- ✅ 降权而非直接删除（给恢复机会）
- ✅ 通知用户并说明原因
- ✅ 提供一键恢复选项
- ✅ 记录清理历史用于系统学习

**不做**：
- ❌ 静默删除（用户必须知情）
- ❌ 不可逆操作（7天内可撤销）
- ❌ 仅凭单一指标决策（多维度综合判断）

## 十九、历史删除

### 19.1 删除范围

**可以删除**：
- ✅ 搜索历史记录
- ✅ 浏览历史记录

**不可删除**（红线保护）：
- ❌ 出处树（R-06：不可删除或修改）
- ❌ 案例库（高可信案例永久存档）
- ❌ 推送历史（用于信任分校准）
- ❌ 订阅源（L1/L2）
- ❌ 信任分数据

### 19.2 删除方式

**Bot命令**：
```
/delete history [id]      → 删除单条历史
/delete history all       → 删除全部历史（需二次确认）
/delete history search    → 删除所有搜索历史
/delete history view      → 删除所有浏览历史
```

示例：
```
用户：/delete history all
系统：⚠️ 确认删除全部历史记录？
     此操作不可恢复，但不影响订阅源、出处树、案例库。
     [✅ 确认删除] [❌ 取消]
```

**Web看板**：
```
每条记录旁有删除按钮：[🗑️]

批量操作：
☑️ 全选  ☑️ 最近7天  ☑️ 最近30天
[🗑️ 批量删除]

清空全部：
[🗑️ 清空全部历史记录]
→ 弹出确认框：
  "确认删除全部历史记录？此操作不可恢复。"
  [确认] [取消]
```

### 19.3 删除后处理

```
• 删除操作记录到系统日志（可审计）
• 删除后不提供恢复功能
• 删除历史不影响：
  - 信任分计算
  - 缓存池状态
  - 出处树完整性
  - 案例库
• 历史记录中的链接支持复制（即使记录被删除，链接仍可手动复制保存）
```

### 19.4 红线合规

```
✅ R-06 出处树不可删除：历史记录删除不影响出处树
✅ 可审计：删除操作记录到系统日志
✅ 透明性：删除前明确告知影响范围
✅ 不可恢复：删除后不提供恢复，避免数据混乱
```
